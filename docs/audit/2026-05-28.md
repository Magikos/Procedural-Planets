## Part 3 — New Findings (2026-05-28)

These concern code that did not exist at the last audit (weather, clouds, precipitation, water-volume, render features, docs).

### ➕ NEW-01 — 🟡 EventBus dispatch uses reflection + per-call allocation for instance handlers

**File:** [Assets/Scripts/Core/Events/EventBus.cs](../../Assets/Scripts/Core/Events/EventBus.cs)

The weak-reference redesign (good for leak safety) invokes non-static handlers via `MethodInfo.Invoke(target, new object[] { context })` ([EventBus.cs:77](../../Assets/Scripts/Core/Events/EventBus.cs#L77), [110](../../Assets/Scripts/Core/Events/EventBus.cs#L110)). Each dispatch to an instance subscriber therefore:

- allocates a `new object[1]`,
- boxes the `struct` event into `object`,
- pays reflection-invoke overhead (much slower than a delegate call).

For the current low-frequency events (`PlanetGeneratedEvent`, debug toggles) this is invisible. But the bus is the project's intended decoupling backbone, and future per-frame/per-chunk events (chunk loaded, entity spawned, weather tick) would make this a measurable GC and CPU cost.

**Recommendation:** Keep the weak-reference *target* for lifetime safety, but rebuild the open delegate once at subscribe time instead of invoking via `MethodInfo` each time — e.g. cache an `Action<object, TEvent>` created from the method, or store a strong `Action<TEvent>` and rely on the existing `Unlisten`/`IsDead` cleanup. This also subsumes SUGG-01.

### ➕ NEW-02 — ⚪ `WeatherManager` resolves `PrecipitationController` via scene scan instead of the registered service

**File:** [WeatherManager.cs:232,424](../../Assets/Scripts/Planet/WeatherManager.cs#L424)

`UpdateWeatherAggregateDiagnostics()` calls `FindAnyObjectByType<PrecipitationController>()`. It's gated by `ShowWeatherDiagnostics` and a throttle, so it is *not* a per-frame hot path — but `PrecipitationController` already registers `IPrecipitationDebugControl` in the `ServiceLocator`, and `StormThreshold` could be exposed there. Using the locator removes the scene scan and the concrete-type dependency. Low severity.

### ➕ NEW-03 — ⚪ Render features fall back to `FindAnyObjectByType` when their controller cache is null

**Files:** [AtmosphereRenderFeature.cs:34](../../Assets/Scripts/Planet/Atmosphere/AtmosphereRenderFeature.cs#L34), [CloudRenderFeature.cs:41](../../Assets/Scripts/Planet/Clouds/CloudRenderFeature.cs#L41), [PrecipitationRenderFeature.cs:42](../../Assets/Scripts/Planet/PrecipitationRenderFeature.cs#L42)

Each feature caches its controller, but the fallback runs `FindAnyObjectByType` whenever the cache is null. In the normal case the controller exists and this runs once. In the edge case where the controller is absent (e.g. atmosphere disabled), the scan runs on every render setup. Consider resolving through the `ServiceLocator` (these controllers are all registered) and/or caching the null result to avoid repeated scans. Low severity.

### ➕ NEW-04 — 🔵 `Planet.DestroyChildrenImmediate()` is now misnamed

**File:** [Planet.cs:162](../../Assets/Scripts/Planet/Planet.cs#L162)

The BUG-01 fix changed the body to use `Destroy()`, but the method is still called `DestroyChildrenImmediate`. The name now actively misleads a reader into thinking it uses `DestroyImmediate`. Rename to `DestroyChildren()`.

### ➕ NEW-05 — 🟡 DOC-01: Memory-bank docs significantly lag the codebase

**Files:** `.amazonq/rules/memory-bank/{structure,product,tech}.md`

`structure.md`'s directory tree and `product.md`'s "Current Phase" predate large, shipped subsystems: `WeatherManager`/`SphericalWeatherGrid`, `CloudController`/`CloudRenderFeature`/`CloudNoiseGenerator`, `PrecipitationController`/`PrecipitationRenderFeature`/`WeatherLightningController`, `WaterMeshBuilder`/`WaterVolumeRenderFeature`/`WaterWakeController`, the SDF text stack (`Core/Text/*`), `LoadingManager`/`ProgressTracker`/`ProgressHandle`, `DebugRegistry`/`DebugCaptureController`/`DebugInputRelay`/`DebugModeConstants`, `ShaderGlobalsController`, `QualityController`, and the `IEarlyInitialize`/`ILateInitialize` bootstrap ordering. The `code-health-checklist.md` explicitly requires "Memory bank files … up to date," so this is a tracked hygiene item. The `water.md` reference, by contrast, is current and excellent.

**Recommendation:** Refresh `structure.md` (directory tree + startup flow), `product.md` (current phase: biomes + water + weather + clouds + atmosphere are in), and `tech.md` (the new render features and the loading/progress system). Add a one-line "code health" entry per audit going forward.

### ➕ NEW-06 — ⚪ Per-frame global shader writes in `Update()` are unconditional

**Files:** [AtmosphereController.cs:53-61](../../Assets/Scripts/Planet/Atmosphere/AtmosphereController.cs#L53), [WeatherManager.cs:142-143](../../Assets/Scripts/Planet/WeatherManager.cs#L142)

`AtmosphereController.Update()` re-pushes ~25 `Shader.SetGlobal*` values every frame; `WeatherManager.Update()` pushes wind globals every frame. The sun direction genuinely changes each frame, so most of this is justified — but the static parameters (Rayleigh/Mie coefficients, scale heights, step counts, sun-disc params) only change when `Settings` changes. Splitting "dynamic per-frame" from "push-on-change" would trim redundant native calls. There is already a `ShaderGlobalsController` that could centralize this. Low severity; note it only if profiling shows it.

# Improvements & Recommendations — 2026-05-28

This section is forward-looking: ideas to make the project better, beyond fixing audit findings. Ordered by leverage. Nothing here is urgent; these are for the "after the audit fixes" conversation.

## A. Reliability & developer velocity

### IMP-01 — Add an EditMode/PlayMode test assembly
There is `com.unity.test-framework` in the manifest but no tests. The most valuable, cheapest-to-write tests for this project are **determinism tests**: generate a planet with a fixed seed, hash the elevation array, and assert it's stable across runs and across a background-thread regeneration. The same applies to `PoissonDiscSphereSampling` and `BiomeRegistry.Resolve`. These guard the project's core promise ("same seed → identical output") and would have caught BUG-02-class races automatically. Put them in a `Tests/` folder with its own asmdef referencing `Core` + `Planet`.

### IMP-02 — Typed EventBus clear-registry
`GameBootstrap.OnDestroy()` hand-maintains a list of 12 `EventBus<T>.ClearAll()` calls ([GameBootstrap.cs:30-44](../../Assets/Scripts/Core/Services/GameBootstrap.cs#L30)). Every new event type must be remembered here or it leaks across scene reloads. Have `EventBus<T>` register a `ClearAll` delegate into a static `EventBusRegistry` the first time it's used, and let `GameBootstrap` call `EventBusRegistry.ClearAll()` once. This was the original audit's "cleaner long-term fix" and removes a whole class of future leaks.

### IMP-03 — A single debug-mode source of truth
Debug functionality now spans `DebugCaptureController`, `DebugInputRelay`, `DebugRegistry`, `DebugModeConstants`, `WaterDebugModule`, plus the F10 enum documented in `water.md` (40+ modes). This is powerful but sprawling. Consider consolidating the mode list + descriptions into one registry that both the input layer and the overlay read from, so adding a debug mode is a one-line change. (Partly done via `DebugRegistry` — finish the consolidation.)

## B. Performance (ahead of LOD / chunks)

### IMP-04 — Burst + Jobs for noise and mesh generation
The roadmap already plans this (`tech.md`), and it's the highest-impact perf work available. `ShapeGenerator.EvaluateElevation` and `TerrainFace.CalculateMeshData` are currently `Parallel.For` over managed code with a shared `MinMax`. Converting noise evaluation to a Burst-compiled `IJobParallelFor` over `NativeArray<float3>` would cut generation time dramatically and is a prerequisite for streaming chunk LOD without hitches. `local-only/LOD-Planets-in-Unity-master` is the reference here.

### IMP-05 — EventBus allocation cleanup
Covered as NEW-01, repeated here because it's a "make it better" as much as a "fix": a non-allocating dispatch path makes the bus safe to use for the high-frequency gameplay events that Phases 8–12 will introduce (chunk load/unload, entity spawn/death, world actions).

## C. Architecture for the road ahead

### IMP-06 — Stand up the chunk/world-action skeleton early
The architecture doc describes `IChunkManager`, `IChunkDataProvider`, `IChunkDeltaStore`, `IWorldAction`, `ISaveManager` ([00-code-architecture.md:30-55](../phases/00-code-architecture.md#L30)). `IWorldAction`/`WorldActionManager` exist; the chunk side does not. Even a thin, non-functional skeleton (interfaces + a no-op in-memory `IChunkDeltaStore`) would let water, spawning, and marching-cubes work be designed against the real seams instead of against `Planet` directly — avoiding a painful retrofit at Phase 9–10.

### IMP-07 — Promote project code into namespaces deliberately
`guidelines.md` flags the global namespace as "current legacy state, not a permanent rule." As the file count climbs (now ~90+ scripts), the lack of namespaces makes the global symbol table noisy and invites accidental name collisions (there are already two `Test`-style classes). A staged move to `ProceduralPlanets.Core`, `ProceduralPlanets.Planet`, etc. (matching the existing asmdefs) is much cheaper now than after Phases 10–14 add player/building/crafting/networking code.

## D. Housekeeping

### IMP-08 — Decide the fate of the `Test` fixtures
`Test.cs` and `TestPoissonDiscSphereDraw.cs` are editor-only Gizmo drawers. If they're still useful, move them to `Assets/Editor/` and fix their naming (CONV-01/02). If the future test assembly (IMP-01) supersedes them, delete them. Either resolves the convention findings permanently.

### IMP-09 — Keep `water.md` as the model for subsystem docs
The water context doc is genuinely excellent — it captures *why* each decision was made and what was tried and rejected, which is exactly what saves future debugging time. As atmosphere, clouds, and weather stabilize, give each a similar `*-reference.md` (atmosphere already has one). This is the project's best documentation habit; institutionalize it.

### IMP-10 — Refresh the memory bank (DOC-01)
Not optional long-term: the structure/product/tech docs are the first thing any new agent or contributor reads, and they currently describe a project two-thirds the size of what exists. Budget an hour to bring them current and add the directory entries listed in NEW-05.
