## Findings

### SH-01 — 🟡 `Ocean.shader` uses `_Time.y` for wave phase

**File:** [Ocean.shader:181,331](../../Assets/Graphics/Shaders/Ocean.shader#L181)

```hlsl
float theta = dot(positionTS, directionTS) * k + _Time.y * speed + phase;   // L181
float waveTime = _Time.y * timeScale;                                        // L331
```

`Ocean.shader` is the **only** animated shader still using `_Time.y`. `Cloud.shader`, `Precipitation.shader`, and `WaterVolume.shader` all use `_GameTime`, which `Math.hlsl` documents as: *"Precision-safe game time. Set from CPU: Time.time % 3600f. Use this instead of _Time.y to avoid float32 precision loss after long sessions."* It is set every frame by [ShaderGlobalsController.cs:37](../../Assets/Scripts/Core/Services/ShaderGlobalsController.cs#L37) (`Mathf.Repeat(Time.time, 3600)`).

`_Time.y` is seconds since level load and grows unbounded; `sin(_Time.y * k)` with a large argument loses float32 precision, so over a long session the waves stutter, band, and eventually "freeze." This is exactly the failure `_GameTime` was introduced to prevent.

**Fix (will do during ocean work):** replace both `_Time.y` with `_GameTime`. `_GameTime` wraps hourly, which causes a one-frame phase discontinuity every hour — the same trade every other shader already accepts, and far better than precision rot.

### SH-02 — 🟡 (latent) Duplicate uniform declarations in two includes

**Files:** [WeatherSampling.hlsl:8-12](../../Assets/Graphics/Shaders/Includes/WeatherSampling.hlsl#L8), [CloudShadows.hlsl:6-15](../../Assets/Graphics/Shaders/Includes/CloudShadows.hlsl#L6)

Both files declare `_CloudWeatherMap`, `sampler_CloudWeatherMap`, and `_CloudWeatherRotation` (and each has its own `CubeFaceUv`/`CloudShadowCubeFaceUv`). Their include guards differ (`WEATHER_SAMPLING_INCLUDED` vs `CLOUD_SHADOWS_INCLUDED`), so the guards do **not** prevent cross-file duplication.

Today this compiles because no shader includes both: Cloud/Precipitation include `WeatherSampling`; Ocean/WaterVolume/PlanetVertexColor include `CloudShadows`. But it's a footgun — the first time a shader needs both (e.g. clouds reading cloud-shadow density, or water calling `SampleWeather`), it will fail with redefinition errors.

**Recommendation:** extract the shared cube-weather declarations (`_CloudWeatherMap` + sampler + `_CloudWeatherRotation` + one `CubeFaceUv`) into a single `WeatherCommon.hlsl` that both include. Low priority until something needs both, but cheap to do now.

### SH-03 — 🟡 `Math.hlsl SmoothMax` is broken (and unused)

**File:** [Math.hlsl:35-40](../../Assets/Graphics/Shaders/Includes/Math.hlsl#L35)

```hlsl
float SmoothMax(float a, float b, float k) {
    k = min(0, -k);                              // → k ≤ 0 always
    float h = max(0, min(1, (b - a + k) / (2 * k)));  // 2*k ≤ 0; divide-by-zero when k==0
    return a * h + b * (1 - h) - k * h * (1 - h);
}
```

With the usual positive smoothing factor, `k = min(0,-k)` yields a negative `k`, so `2*k` is negative (inverted blend) and `k==0` divides by zero → NaN. `SmoothMin` directly above is the correct IQ form (`k = max(0,k)`). `SmoothMax` is not called by any shader, so it's currently dead.

**Fix:** delete it (lowest risk, since unused), or correct it to `return -SmoothMin(-a, -b, k);`.

### SH-04 — ⚪ Doc drift: `OpticalDepth.compute` is used

`atmosphere-reference.md` still lists `OpticalDepth.compute` as "UNUSED in v3 (kept for future LUT optimization)". In the current code it **is** used: [AtmosphereController.BakeOpticalDepth](../../Assets/Scripts/Planet/Atmosphere/AtmosphereController.cs#L135) dispatches it into `_BakedOpticalDepth`, and [Atmosphere.hlsl SunOpticalDepth](../../Assets/Graphics/Shaders/Includes/Atmosphere.hlsl#L65) samples that LUT every view step. (`tech.md`/`structure.md` were corrected in the DOC-01 refresh; `atmosphere-reference.md` still needs the one-line fix.)

### SH-05 — 🟡 (perf) `Ocean.shader` fragment is expensive, partly for debug-only outputs

**File:** [Ocean.shader:286-428](../../Assets/Graphics/Shaders/Ocean.shader#L286) (`ComputeSurfaceWaves`)

Every water pixel evaluates ~7 `EvaluateSurfaceWave` layers, a domain warp, a 3-projection triplanar `SurfaceCellPattern` (each projection is a 9-cell `SurfaceVoronoi`, so ~27 voronoi cells/pixel), the `waveProof` line-pattern block (many `ValueNoise` + trig calls), plus foam/glint. Several results — `waveProof`, much of `rippleSignal`, the cell-pattern detail — feed mainly debug views (`DEBUG_SURFACE_FX_PROOF`, etc.) or contribute marginally to the final color (`waveProof * 0.20` into the crest driver). On a ~220k-vert ocean filling the screen this is a heavy fragment.

**Recommendation (during ocean work):** gate the debug-only computations behind the debug branch so the production path skips them, and re-evaluate whether the triplanar voronoi cell pattern earns its cost versus a cheaper detail-normal source. This also frees headroom for real wave geometry (SH-06).

### SH-06 — ⚪ (design) Waves are fragment-normal-only — no vertex displacement

**File:** [Ocean.shader:559-571](../../Assets/Graphics/Shaders/Ocean.shader#L559) (`vert`)

The vertex shader transforms position and passes through vertex-color water data — it applies **no** wave height to the geometry. All "waves" are normal perturbations computed in the fragment shader (`ComputeSurfaceWaves` → `rippleNormalWS`). This matches the documented decision in `water.md` (the global radius-5000 water mesh is far too coarse for small vertex waves), but it is the fundamental reason the ocean reads as a flat shaded sheet rather than moving water.

**This is the central lever for the upcoming work**, not a bug. Options to weigh: a denser near-camera water patch (or tessellation / LOD ring) that *can* carry real displacement; a screen-space/parallax fake for height; or committing to normal-only and tuning lighting/glint/foam to sell it. Decide this before tuning values.

### SH-07 — ⚪ `_WorldSpaceCameraPos` declared `float4` in Common.hlsl

[Common.hlsl:25](../../Assets/Graphics/Shaders/Includes/Common.hlsl#L25) declares it `float4` where URP's own headers use `float3`. The underlying global is a `Vector4` (set via `Shader.SetGlobalVector`), and every use is `.xyz`, so this is harmless — noted only so it isn't mistaken for a bug if the two declarations ever meet in one translation unit.
