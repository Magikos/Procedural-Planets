Water & Ocean System

How every moving part fits together — generation, rendering, and the code that drives it. Written so you can read it top-to-bottom and understand the system well enough to give precise feedback.

The one-paragraph version

A planet's water is one runtime-generated mesh sitting at sea level, clipped to the basins where terrain dips below sea level. Each water vertex carries three numbers baked into its color — depth, distance from shore, body size — and almost every visual decision (wave size, foam, transparency, caustics) is driven by those three numbers. Rendering happens in three layers: a full-screen underwater volume drawn before transparents, the transparent surface (color + waves + foam + glint), and the atmosphere post-process on top. The surface mesh is displaced by Gerstner-style swell in its vertex shader for real 3-D waves.

1. Mental model

Hold these four ideas and the rest follows:

  1. One ocean mesh, clipped to basins. There is no separate lake/ocean object and no camera-following patch. WaterMeshBuilder builds a single mesh covering every place the terrain is below sea level. Ponds, lakes, and oceans are all the same mesh — they differ only by the per-vertex body size value.
  2. Vertex colors are the data bus. The mesh's vertex colors are not colors — they're a packed data channel (depth, shore distance, body factor). The surface shader, the volume shader, and the prepass all read the same three numbers. When you wonder "how does the shader know X?", the answer is usually "from a vertex color channel."
  3. Three render layers, drawn in a fixed order. Underwater volume (full-screen, before transparents) → surface (transparent queue) → atmosphere (post-process). Each owns a different visual job and they hand off via depth + a shared "water interface" texture.
  4. Everything is global-shader-driven and event-driven. The planet raises one PlanetGeneratedEvent when generation finishes; weather/celestial systems push Shader.SetGlobal* values (wind, sun, sea radius, time) every frame. The water shaders read those globals — they're not wired with direct references.

2. The three rendering layers

LayerWhat it drawsShaderWhen
Volume (underwater body)Depth fog, caustics on the seabed, refraction/distortion of the bottom, the "looking through deep water" tintWaterVolume.shader (full-screen)Before transparents
Surface (the water sheet)Water color by depth, waves (vertex swell + detail normals), foam, sun glint, fresnel sky reflectionOcean.shader (on the mesh)Transparent queue
AtmosphereScattering/haze over distant water, sky color, light shafts — fades water into the horizonAtmosphere.shader (full-screen)Post-process

Why split it this way?

Transparent surfaces can't easily read "what's behind me through the water." So the volume layer runs first and bakes the underwater look into the color buffer; the transparent surface then blends on top. A shared _WaterInterfaceTexture (written by the prepass) lets later passes — including the atmosphere — know where water is on screen so they can behave correctly at the waterline.

The two water-volume passes are ScriptableRenderPasses enqueued by WaterVolumeRenderFeature, both at RenderPassEvent.BeforeRenderingTransparents. The surface is a normal transparent material, so URP draws it after them automatically. The atmosphere is its own ScriptableRendererFeature running as a post-process.

4. Generation pipeline (when does water get built?)

Startup is orchestrated by LoadingManager, which runs IEarlyInitialize then ILateInitialize components in priority order. Planet is an ILateInitialize; water is built inside its generation.

LoadingManager.InitializeAsync └─ Planet.LateInitialize → GeneratePlanetAsync() 1. Initialize() build shape/color generators, 6 terrain faces 2. GenerateMeshAsync() terrain meshes (parallel, background thread) 3. CommitElevationRange() publish final elevation min/max 4. GenerateColorsAsync() biome vertex colors on the terrain 5. GenerateWaterAsync() ◄── builds the water mesh + material 6. raise PlanetGeneratedEvent(center, radius, seaLevelRadius, ...) → CelestialManager, AtmosphereController, WeatherManager, camera react

Inside Planet.GenerateWaterAsync()

Assets/Scripts/Planet/Planet.cs

// 1. Skip entirely if this planet has no oceans.
if (!_planetSettings.HasOceans) { _waterObject?.SetActive(false); return; }

// 2. Make/reuse the "Water" child GameObject (MeshFilter + MeshRenderer, shadows off).
// 3. Describe the build: radius, ocean level, depth ranges, body threshold — scaled to planet size.
var buildSettings = new WaterMeshBuilder.Settings { PlanetRadius = ..., OceanLevel = ..., ... };

// 4. Build the mesh on a worker thread, polling progress each frame so the loading bar moves.
var computeTask = Task.Run(() =>
    WaterMeshBuilder.Compute(terrainFaces, buildSettings, p => Volatile.Write(ref buildProgress, p)));
while (!computeTask.IsCompleted) { _progressHandle.Report(0.90f + 0.06f*buildProgress, "Building water bodies..."); await NextFrame; }
var waterMeshData = await computeTask;

// 5. Upload the mesh, create/assign the Ocean material, push tunables into it.
WaterMeshBuilder.Apply(waterMesh, null, waterMeshData);
UpdateWaterMaterial(_waterMaterial);

Who owns what here

  • Planet.cs — orchestrates: makes the GameObject, calls the builder, creates the material, sets material constants (colors, depths, wave/foam/glint amounts). It does not know how waves or fog look.
  • WaterMeshBuilder.cs — pure data: turns the 6 terrain faces into a clipped water mesh with the vertex-color contract. No Unity rendering, runs on a worker thread.
  • The shaders — own the look, reading material constants + vertex colors + global state.

5. The vertex-color data contract most important section

Every water vertex's color encodes three normalized values. This is the single most load-bearing idea in the whole system — learn it and the shaders become readable.

ChannelMeaningRangeDrives
color.rdepth01 — normalized water depth (how far the seabed is below sea level)0 = at surface, 1 = max depthwater color (shallow→deep), swell strength, absorption/opacity, caustic fade
color.gshore01 — normalized distance from the shoreline0 = right at shore, 1 = far from shoreshoreline foam, wave calming near shore, terrain-contact fades
color.bbody01 — "large body" factor (is this a pond or an ocean?)0 = tiny pond, 1 = large oceanswell wavelength/amplitude (ponds stay calm), whitecaps, open-water effects

This is how ponds differ from oceans

A small pond's vertices have body01 ≈ 0 and are mostly shallow + near-shore, so the swell code multiplies its amplitude/wavelength down to almost nothing — calm water. An open ocean has body01 ≈ 1, deep depth01, and high shore01, so it gets the full long swell. Same shader, same mesh — different vertex data.

In every shader you'll see this destructure at the top of the fragment (or vertex) stage:

float depth01 = saturate(input.waterData.r);
float shore01 = saturate(input.waterData.g);
float body01  = saturate(input.waterData.b);

6. WaterMeshBuilder — how the mesh and the contract are produced

Assets/Scripts/Planet/WaterMeshBuilder.cs · entry point Compute(faces, settings, onProgress)

Compute() 1. BuildGlobalWaterData(faces) ◄── the heavy phase (~45% of build) • walk all 6 cube-sphere faces as ONE graph (shared seam vertices, keyed by quantized direction, so faces don't get independent data) • mark every vertex wet/dry (terrain elevation vs sea level) • ClassifyWaterBodies(): flood-fill connected wet regions → small regions = ponds (low body01), big regions = oceans (high body01) • shore-distance BFS: distance from each wet vertex to the nearest dry vertex → shore01 2. for each of the 6 faces: ProcessFace(...) • emit water surface triangles only where wet • clip the shoreline edge slightly UNDER the terrain (avoids a hard seam) • write vertex color = (depth01, shore01, body01) • also emit a "WaterVolumeLip" mesh: an extended skirt under the terrain used only by the volume prepass for coverage (never rendered visibly) 3. return MeshData (vertices, normals, colors, triangles, + lip mesh + stats)

Why a global graph (not per-face)?

The planet is a cube-sphere: 6 separate face meshes. If each face computed body/shore data independently, you'd see straight seams along cube edges (a square-ish shoreline). BuildGlobalWaterData stitches the faces by direction so flood-fill and shore-distance cross face boundaries seamlessly. If you ever see a suspiciously straight water edge, this is the suspect.

7. The ocean surface shader (Ocean.shader)

Assets/Graphics/Shaders/Ocean.shader — one transparent pass: Blend SrcAlpha OneMinusSrcAlpha, ZWrite Off, ZTest LEqual. ZTest LEqual at sea level is what clips the surface to basins for free (dry land is nearer in depth and occludes it).

Vertex stage — geometry + base normal

Varyings vert(Attributes input)
{
    float3 positionWS   = TransformObjectToWorld(input.positionOS.xyz);
    float3 planetNormal = normalize(positionWS - _PlanetCenter);
    float3 waterData    = saturate(input.color.rgb);   // depth, shore, body

    // NEW: real wave geometry — push the vertex out along the planet normal.
    float swellHeight; float3 swellNormal;
    ComputeOceanSwell(positionWS, planetNormal, waterData.r, waterData.g, waterData.b, swellHeight, swellNormal);
    positionWS += planetNormal * swellHeight;

    output.positionWS = positionWS;
    output.normalWS   = swellNormal;   // fragment perturbs this with fine detail
    output.waterData  = waterData;
    output.positionCS = TransformWorldToHClip(positionWS);
}

Two-layer waves

The surface has two wave systems working together (the classic GPU Gems model):
  • Geometric swell — ComputeOceanSwell in the vertex shader. Moves actual geometry → silhouette, parallax, big rolling waves. Limited to long wavelengths the mesh can represent (≳70 m). See §8.
  • Detail normals — ComputeSurfaceWaves in the fragment shader. No geometry, just normal perturbation → small ripples, glint sparkle, surface texture. Can be arbitrarily fine.

8. The swell — real waves on the mesh

This is the layer that makes the ocean read as 3-D water rather than a flat sheet. It lives in ComputeOceanSwell() in Ocean.shader and follows Sebastian Lague's planetary approach (radial vertex displacement).

void ComputeOceanSwell(positionWS, planetNormal, depth01, shore01, body01,
                       out swellHeight, out swellNormal)
{
    // 1. ENERGY: where are waves allowed? Calm near shore + in shallow + in small bodies.
    float openWater01 = smoothstep(0.30, 0.85, body01);   // pond → ocean
    float deepWater01 = smoothstep(0.015, 0.16, depth01);  // shallow → deep
    float shoreFade   = smoothstep(0.015, 0.16, shore01);  // shoreline → open
    float energy = saturate(0.5 + wind01*0.5) * deepWater01 * shoreFade;

    // 2. SCALE by body size: ponds get short, low ripples; oceans get long, tall swell.
    float wavelength = _SwellWavelength * lerp(0.42, 1.0, openWater01);
    float amplitude  = _SwellAmplitude  * lerp(0.18, 1.0, openWater01) * energy;

    // 3. SUM 3 waves (reusing EvaluateSurfaceWave) → height + gradient,
    //    projected onto a world-stable tangent frame (BuildPlanetWaveAxes).
    //    ...accumulates `height` and `gradientTS`...

    // 4. Displace radially; derive the normal from the height gradient.
    swellHeight = height;
    swellNormal = normalize(planetNormal - tangentialSlope);
}

And in the vertex shader: positionWS += planetNormal * swellHeight; — that single line is what turns the flat sheet into rolling water across the entire ocean. Because it operates on the world-fixed mesh, the waves stay attached to the water (they don't slide when the camera moves).

The mesh-resolution ceiling

The water mesh has ~21 m between vertices. A wave can only be represented if its wavelength is well above ~2× that (≳70 m). So the swell does big rolling waves; small choppy detail must come from the fragment normals (§7). If you crank _SwellWavelength below ~70 the crests turn jagged — that's the mesh under-sampling the wave, not a bug. Fix: raise the wavelength, or (future) tessellate / add a denser near-camera ring.

Why Gerstner-style (and why it matters for boats later)

The swell is a closed-form height(position, time) function. That means the same math can be evaluated on the CPU to float boats and swimmers on the waves — no GPU readback. (An FFT ocean looks great but its height lives in a texture that's painful to query per-point on the CPU.) When boats arrive, ComputeOceanSwell gets a C# twin.

9. The water volume (underwater body)

Assets/Graphics/Shaders/WaterVolume.shader — a full-screen pass composited before the surface. It answers "what does it look like to peer into / through the water?"

What it produces (per screen pixel that's behind water):

  • Depth fog & absorption — the further light travels through water, the more it's tinted toward deep blue and dimmed. Computed from an optical-depth estimate (VolumeOpticalDepth) using the seabed distance and the camera ray's path length through the sea sphere.
  • Caustics — animated bright light patterns on the seabed (ComputeReceiverCaustics). See §13.
  • Refraction / bottom distortion — wobbles the seabed image by sampling the color buffer at an offset (ComputeBottomDistortion).
  • Far-shore waterline — distant coastlines seen across the curve of the ocean get tinted by the long water path so they don't read as a hard bright line.

It reconstructs the seabed world position from the camera depth texture, checks it's below sea level, and only then applies the underwater look:

float receiverDistance = LinearEyeDepth(rawDepth, _ZBufferParams) * viewLength;
float3 receiverWS = _WorldSpaceCameraPos + rayDir * receiverDistance;  // seabed point
float waterDepth = _SeaLevelRadius - length(receiverWS - _PlanetCenter); // how deep?
if (waterDepth <= 0) ...skip...   // above sea level → not underwater

10. The prepass & render feature (the plumbing)

Assets/Scripts/Planet/WaterVolumeRenderFeature.cs finds the Water object, copies material settings into the prepass + volume materials, and enqueues two passes:

PassJobOutput
WaterVolumePrepassDraw the water mesh (and the under-terrain "lip" skirt) recording where water is and its data_WaterInterfaceTexture / _WaterVolumeData = (forwardDepth, depth01, shore01, body01), set as global textures
WaterVolumeCompositeFull-screen: read color + that texture + scene depth, run WaterVolume.shaderreplaces cameraColor with the underwater-composited image

The prepass writes its data into an off-screen R16G16B16A16 texture and publishes it globally with SetGlobalTextureAfterPass. Both the volume composite and the atmosphere read it — that's how the atmosphere knows to stop light shafts at the water surface.

The "lip" mesh

WaterMeshBuilder emits a second, invisible mesh (WaterVolumeLip) that extends slightly under the dry terrain. It's drawn only into the prepass coverage texture so the underwater volume reaches all the way to the true waterline without the visible surface poking through the beach. You'll see it referenced in the prepass passes and in several F10 debug modes.

Global switch: _WaterVolumeEnabled

If no water object is found, the feature sets _WaterVolumeEnabled = 0 and other shaders (atmosphere) skip their water-aware branches. When water exists it's 1. Handy to know when debugging "why is the atmosphere ignoring the water."

11. Weather & wind coupling

Wind and storms are global shader values pushed every frame by WeatherManager:

Shader.SetGlobalVector(_windDirectionId, WindDirection);
Shader.SetGlobalFloat(_windSpeedId, WindSpeed);
  • _WindDirection orients the wave axes (BuildPlanetWaveAxes) so swell and ripples travel with the wind.
  • _WindSpeed (normalized as wind01 = _WindSpeed/5) scales wave energy, chop, and whitecaps. Low wind → glassy; high wind → choppy with whitecaps.
  • Storms are sampled from the cloud weather map via SampleCloudShadowWeather(normal).g in CloudShadows.hlsl. The surface uses the storm value only for foam/whitecaps — deliberately not for wave height, because feeding local storm cells into displacement stamped visible cyclone/ring shapes into the water.

12. Day / night coupling

The sun direction is the global _SunParams (set by AtmosphereController from CelestialManager). Local day/night at a water point is daylight = smoothstep(-0.08, 0.18, dot(planetNormal, sunDir)).

  • Water color, glint, and foam all multiply down toward near-zero at night (foam is gated to ~5% so it doesn't glow on the dark side).
  • _NightAmbientIntensity (a global, also used by terrain) provides a faint night floor.
  • The moon contributes to underwater caustic light via _MoonParams/_MoonIntensity in the volume shader.

13. Caustics (the seabed light patterns)

Computed in WaterVolume.shader · ComputeReceiverCaustics(). Caustics only appear on submerged surfaces that are lit and not too deep.

ComputeReceiverCaustics(seabedPoint, ray, ...) • gate: must be underwater, lit (sun/moon facing + not cloud-shadowed), shallow enough • CausticPattern(): triplanar animated Voronoi, dual-layer interference (c1*c2) → bright branching cells, warped over time • CausticPrismColor(): RGB fringing along the caustic ridges (chromatic dispersion) • output: causticColor * intensity, faded by depth and water path
  • Pattern — CausticVoronoi + domain warp gives the organic branching look; contrast via pow(caustic, _CausticContrast).
  • Chromatic — CausticPrismColor splits the ridge edges into red/green/blue fringes for the "whimsical" prism look you asked about. (Roadmap: push this further by sampling the pattern per-channel with a small phase offset so the cells themselves — not just edges — are RGB-split.)
  • Fades — depthFade = exp(-waterDepth / _CausticDepth) (gone in deep water) and a path fade (gone at grazing distance).

14. Debug workflow (F10) how to give good feedback

The fastest way to tell which layer is responsible for something is the F10 capture system. Pressing F10 writes a set of PNGs + .txt sidecars to local-only/debug-screenshots/. The sidecar logs camera position, sun state, sea radius, and the live water material values — read it first.

The mode is the global int _OceanDebugMode; names/constants live in DebugModeConstants.cs (C#) mirrored by Includes/DebugModes.hlsl (shader), and are registered in WaterDebugModule.cs.

The modes you'll use most

WaveHeight (9) / WaveSlope (10) / Normals (6)the detail-wave field"are ripples being computed here?"

How to report a water issue efficiently

  1. Note the camera situation (on shore / underwater / high up; day or night).
  2. Run F10 and check SurfaceOnly vs VolumeOnly vs WaterOff — that localizes the layer.
  3. If it's the surface, check WaveHeight/Foam/Glint; if the volume, check VolumeMask/VolumeOptical/Caustics*.
  4. Tell me the mode where the artifact appears and the mode where it vanishes. That pair almost always pinpoints the code.
